# 会话与运行时分层

## 适用场景

当项目同时存在：

- session 级能力
  - snapshot
  - resume
  - memory extract
  - knowledge sync
  - gateway reply 注入
- orchestration 级能力
  - single agent 对话执行
  - multi-agent network 路由
  - HITL 编排

最容易犯的错误，就是把这两类职责继续塞进一个“大 session 类”里。

## 推荐分层

### infrastructure/session

这一层只回答：

- 当前 chat 是否有活跃任务
- 任务如何启动、终止、恢复
- 任务结束后如何保存 snapshot
- 如何把外部用户回复注入到当前等待点
- 如何在收尾时做 memory / knowledge 处理

换句话说，这层关心的是“任务壳子”。

### orchestration

这一层只回答：

- 一次任务实际如何执行
- 谁是下一位说话者
- 是否需要向人提问
- transcript 如何推进
- 运行结束时的 `status / transcript / last_speaker` 是什么

换句话说，这层关心的是“任务过程”。

### agents

这一层只回答：

- agent 怎么创建
- 用哪些工具
- 有哪些 prompt / contract
- single / network 各自需要什么 agent 能力

换句话说，这层关心的是“参与者配置”。

## 一个实用判断标准

当你在写 session 代码时，如果开始出现下面这些内容，就说明职责已经串层了：

- `a_run_group_chat_iter`
- `DefaultPattern`
- `NetworkSwarmRuntime`
- `next_step` 路由决策
- handoff message 拼接

这些都属于 orchestration，不该继续留在 session shell 里。

## 本项目当前做法

项目当前采取的是：

- `AgentSession`
  - chat 级生命周期与收尾
- `SingleAgentRuntime`
  - legacy single 模式执行
- `NetworkSwarmRuntime`
  - beta network 专家模式执行
- `create_session_runtime()`
  - 根据 mode 选择 runtime

这样做的直接收益是：

1. session 壳层不再需要同时维护两套执行路径
2. orchestration 的变更不会继续污染 gateway / snapshot / memory 逻辑
3. 新增第三种 runtime 时，不需要再往 session 类里堆新的 `_run_xxx()` 分支

## 经验

1. “session” 和 “runtime” 不是同义词。
2. 迁移到 beta network 后，如果 session 类里还保留大量 group chat 执行细节，通常说明拆分还没做完。
3. 命名必须跟职责一致；名字错了，后续维护者就会持续做错抽象判断。
