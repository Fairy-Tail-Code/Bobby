# AG2_openharness 长期记忆系统 — 开发需求文档

> 基于 Claude Code (cc-haha) 记忆架构的逆向分析，结合 AG2 框架能力适配。
> 本文档足够详细，Agent 拿到后可直接指导开发。

---

## 一、系统总览

### 1.1 核心设计哲学

记忆系统存储的是**不可从代码/文件/git 推导的知识**——用户偏好、项目决策、错误经验、外部系统指针。代码模式、架构、文件结构这些都是可推导的，**不应该存入记忆**。

记忆系统由 3 个子系统组成：

| 子系统 | 触发时机 | 职责 |
|--------|---------|------|
| **记忆读写层** | 每次对话 | Agent 主动读写记忆文件，注入 system prompt |
| **实时提取** | 每次对话结束时 | 后台 forked agent 从对话中自动提取新知识 |
| **梦境整理** | 定时（24h + 5次会话） | 后台 agent 整理碎片、合并重复、修剪过期 |

### 1.2 存储介质

**纯文件系统（Markdown + YAML frontmatter），不使用向量数据库或 RAG。**

## 二、记忆分类与存储结构

### 2.1 四类记忆

每类记忆有不同的生命周期、作用域和触发条件：

| 类型 | name | 作用域 | 内容 | 何时保存 | 何时使用 |
|------|------|--------|------|---------|---------|
| **用户记忆** | `user` | 私有（跨项目） | 用户角色、偏好、专业领域、知识水平 | 了解到用户的任何个人信息 | 需要针对用户背景调整回答时 |
| **反馈记忆** | `feedback` | 私有或团队 | 用户对 Agent 行为的纠正/确认（"不要做X"、"对，就是这样做"） | 用户纠正或确认 Agent 行为时 | 指导后续对话中的行为方式 |
| **项目记忆** | `project` | 偏向团队 | 项目工作进展、目标、里程碑、关键决策、bug 状态 | 了解到谁在做什么、为什么做、何时截止 | 需要理解用户请求的深层动机时 |
| **引用记忆** | `reference` | 通常团队 | 指向外部系统的指针（Linear 项目、Slack 频道、Grafana 面板） | 了解到外部系统资源及其用途 | 用户提及外部系统时 |

### 2.2 反馈记忆的 body 结构规范

```
Lead with the rule itself, then a **Why:** line and a **How to apply:** line.
```

示例：
```markdown
---
name: db-testing-policy
description: Integration tests must hit real database
type: feedback
---

Integration tests must hit a real database, not mocks.

**Why:** Prior incident where mock/prod divergence masked a broken migration (2026-Q1).

**How to apply:** All test files under `tests/integration/` must use the real test database fixture, never mock the DB layer.
```

### 2.3 目录结构

```
<project_root>/
├── .openharness/
│   └── memory/                    # 项目记忆根目录
│       ├── MEMORY.md              # 索引文件（≤200行 / ≤25KB）
│       ├── user-preferences.md    # 用户记忆文件
│       ├── feedback-testing.md    # 反馈记忆文件
│       ├── project-milestones.md  # 项目记忆文件
│       └── reference-links.md     # 引用记忆文件
│
├── .openharness/
│   └── memory/
│       └── team/                  # 团队共享记忆（可选）
│           ├── MEMORY.md
│           └── ...
```

**全局用户记忆**（跨项目）：
```
~/.openharness/
└── user-memory/                   # 用户级记忆
    └── profile.md                 # 用户画像
```

### 2.4 记忆文件格式

每个记忆文件都是标准 Markdown + YAML frontmatter，与 Skill 系统格式一致：

```markdown
---
name: 记忆名称（简短，kebab-case）
description: 一行描述（用于索引和检索）
type: user | feedback | project | reference
---

# 记忆标题

记忆正文内容...
```

### 2.5 索引文件 MEMORY.md

`MEMORY.md` 是记忆目录的入口，**不是记忆本身**，而是一个索引：

```markdown
# Memory Index

- [User Preferences](user-preferences.md) — 用户偏好 Go 语言，前端新手
- [DB Testing Policy](feedback-testing.md) — 集成测试必须使用真实数据库
- [Project Milestones](project-milestones.md) — 2026-04-15 前完成 v1.0
- [External Resources](reference-links.md) — Grafana 看板、Linear 项目链接
```

**硬限制**：
- ≤ 200 行
- ≤ 25KB
- 每条索引 ≤ ~150 字符（标题 + 链接 + 一句话 hook）
- 超过限制时追加 `> WARNING: MEMORY.md exceeds size limits. Only partial content loaded.`

## 三、记忆读写层

### 3.1 记忆注入方式（两层）

#### Layer 1 — 全量索引注入

将 `MEMORY.md` 的内容拼接到 Agent 的 system message 中。

- **注入时机**：Agent 创建时，与 skill summaries 一起注入
- **内容**：完整的 `MEMORY.md` 索引文件（可能被截断）
- **位置**：system message 末尾，`## Project Memory` 段落下

注入后的 system message 结构：
```
你是 Planner agent...

## Available Skills
- **repo-surveyor**: ...

## Project Memory
- [User Preferences](user-preferences.md) — 用户偏好...
- [DB Testing Policy](feedback-testing.md) — ...

Call load_memory(file_name) to load full content of any memory file.
```

#### Layer 2 — 按需加载完整记忆

注册 `load_memory` 工具（与 `load_skill` 同模式），Agent 按需调用：

```python
async def load_memory(memory_name: str) -> str:
    """Load the full content of a named memory file.
    Returns the complete markdown content."""
    ...
```

工具注册方式：
- 每个 Agent 注册自己的 `load_memory__<agent_name>` 实例
- 所有 Agent 共享同一个记忆目录
- LLM 调用时返回完整 `.md` 文件内容，作为 `tool_result` 消息进入对话

### 3.2 Agent 主动写记忆

在 Agent 工具中注册 `save_memory` 工具：

```python
async def save_memory(
    name: str,
    content: str,
    memory_type: str = "project",  # user | feedback | project | reference
    description: str = "",
) -> str:
    """Save a new memory file or update an existing one.
    Creates <name>.md in the memory directory and updates MEMORY.md index."""
    ...
```

**安全约束**：
- `name` 只允许 `a-z0-9-` 字符（kebab-case），防止路径穿越
- 文件必须写入 `<project_root>/.openharness/memory/` 目录内
- 写入后自动更新 `MEMORY.md` 索引（保持 ≤200 行限制）

### 3.3 代码结构

```
infrastructure/memory/
├── __init__.py
├── types.py              # MemoryType 枚举，4 类记忆定义
├── paths.py              # 记忆目录路径解析（项目级 / 用户级）
├── store.py              # 文件读写：load / save / delete / list
├── index.py              # MEMORY.md 索引管理（读取、更新、截断）
├── injection.py          # system prompt 注入：build_memory_block()
└── tool.py               # AG2 Tool 注册：load_memory / save_memory
```

## 四、实时记忆提取（Extract Memories）

### 4.1 触发时机

**每次对话结束时**（Agent 完成最终回复，无工具调用），后台自动运行。

### 4.2 实现方式

使用 AG2 的 `ConversableAgent` 创建一个独立的 **提取 Agent**（forked agent 模式）：

1. 从主对话历史中提取最近一次提取以来的新消息
2. 用 LLM 分析这些消息，识别值得持久化的新知识
3. 创建或更新记忆文件
4. 更新 `MEMORY.md` 索引

### 4.3 提取 Agent 的 Prompt 要点

```
你是一个记忆提取器。分析以下对话，提取值得跨会话持久化的知识。

只提取以下类型的信息：
- user：用户的角色、偏好、专业领域
- feedback：用户对 Agent 行为的纠正或确认
- project：项目级决策、里程碑、关键变更
- reference：外部系统指针

不要提取：
- 代码模式、架构、文件结构（可从代码推导）
- 调试方案（修复已在代码中）
- 临时性的对话上下文
- 已在 MEMORY.md 或项目文档中的信息

输出格式：为每条新记忆输出 name、type、description 和完整内容。
```

### 4.4 提取 Agent 的工具限制

提取 Agent 只能使用：
- **FileRead** — 读取现有记忆文件
- **FileWrite / FileEdit** — 仅限 `.openharness/memory/` 目录内
- **Glob / Grep** — 扫描现有记忆
- **禁止**：Bash、浏览器、其他所有工具

### 4.5 互斥机制

- 提取 Agent 和主 Agent 不能同时写记忆文件
- 用文件锁（`memory/.lock`）实现互斥
- 主 Agent 的 `save_memory` 工具写入时设置标记，提取 Agent 跳过已处理的消息范围

### 4.6 代码结构

```
infrastructure/memory/
└── extractor.py          # MemoryExtractor 类
                          # - init_extractor(): 初始化闭包状态
                          # - extract(): 对话结束后调用
                          # - 使用 ConversableAgent 创建 forked agent
                          # - 工具白名单限制
                          # - 互斥锁管理
```

## 五、梦境整理系统（AutoDream）

### 5.1 触发条件（三重门控，按顺序检查）

| 门控 | 条件 | 成本 |
|------|------|------|
| **1. 时间门控** | 距上次整理 ≥ 24 小时 | 1 次 `stat()` 调用 |
| **2. 会话门控** | 上次整理后有 ≥ 5 次新会话 | 扫描会话目录 |
| **3. 锁门控** | 无其他进程持有整理锁 | 1 次文件锁检查 |

**全部通过才触发**。扫描间隔 ≥ 10 分钟（防止时间门控持续通过时的频繁扫描）。

### 5.2 整理流程（四阶段）

```
Phase 1: Orient（定位）
    → ls 记忆目录，了解现有结构
    → 读取 MEMORY.md 索引
    → 粗读现有记忆文件，避免创建重复

Phase 2: Gather（收集）
    → 扫描近期会话记录（JSONL 格式）
    → 查找已有记忆中的过时/错误信息
    → 只搜索已知关键词，不要全文扫描

Phase 3: Consolidate（整合）
    → 将新知识合并到已有的主题文件中（而非创建重复文件）
    → 将相对日期转为绝对日期（"昨天" → "2026-04-12"）
    → 删除被推翻的事实

Phase 4: Prune & Index（修剪索引）
    → 更新 MEMORY.md，保持 ≤ 200 行 / ≤ 25KB
    → 删除指向已过时/已删除记忆的索引条目
    → 过长的索引行（>200字符）缩短，将细节移入主题文件
    → 解决相互矛盾的记忆条目
```

### 5.3 整理 Prompt（核心模板）

```python
DREAM_PROMPT = """# Dream: Memory Consolidation

你正在执行梦境整理——对记忆文件进行反思性审查。将近期学到的知识合成为持久的、组织良好的记忆，使未来会话能够快速定位。

记忆目录: `{memory_root}`

---

## Phase 1 — Orient

- `ls` 记忆目录，查看现有文件
- 读取 `MEMORY.md` 了解当前索引
- 粗读现有主题文件，以便改进而非重复创建

## Phase 2 — Gather recent signal

按优先级查找新信息：
1. 现有记忆是否与当前代码状态矛盾
2. 对话记录中的关键决策（用 grep 窄搜索，不要全文读取）

## Phase 3 — Consolidate

对每条值得记住的知识，写入或更新记忆目录中的文件。
重点：
- 合并到已有主题文件，避免创建近似重复
- 将相对日期转为绝对日期
- 删除被推翻的事实

## Phase 4 — Prune and index

更新 `MEMORY.md` 使其保持在 200 行以内且不超过 25KB。
- 删除过时/错误/已被取代的指针
- 过长的索引行缩短到 ~150 字符
- 添加新重要的记忆指针
- 解决矛盾

---
返回简短的整理摘要。如果没有任何变化，说明原因。
"""
```

### 5.4 整理 Agent 的工具限制

与提取 Agent 相同的只读限制，额外允许：
- **FileEdit / FileWrite** — 仅限 `.openharness/memory/` 目录内
- **Bash** — 仅限只读命令（`ls`, `find`, `grep`, `cat`, `stat`, `wc`, `head`, `tail`）

### 5.5 文件锁与回滚

```
memory/
└── .consolidation.lock    # 整理锁文件
```

锁文件内容：
```json
{"pid": 12345, "acquired_at": "2026-04-13T10:30:00Z", "prior_mtime": 1712985600}
```

- 使用 PID 标识锁持有者
- 超过 1 小时的锁视为 stale（持有者可能已崩溃），可被抢占
- 整理失败时执行完整回滚（将 mtime 恢复为 `prior_mtime`）
- 成功后删除锁文件

### 5.6 代码结构

```
infrastructure/memory/
└── dream.py              # AutoDream 类
                          # - init_dream(): 初始化状态闭包
                          # - check_and_run(): 每轮结束后检查门控
                          # - _run_consolidation(): forked agent 执行四阶段
                          # - _acquire_lock() / _release_lock() / _rollback()
```

```yaml
harness:
```

在 `arun_swarm` 返回后，主流程中调用提取器：

```python
# main.py
chat_result, ctx, last_speaker = await arun_swarm(...)
```

## 八、什么不该存为记忆

以下信息**不应该**保存为记忆（因为可从其他来源推导）：

- 代码模式、命名约定、架构、文件路径、项目结构 → 读取代码
- Git 历史、最近变更、谁改了什么 → `git log` / `git blame`
- 调试方案或修复方案 → 修复已在代码中，commit message 有上下文
- 已在 CLAUDE.md / MEMORY.md / 项目文档中记录的内容
- 临时性的任务细节：正在进行的工作、临时状态、当前对话上下文

## 十、测试要点

### 10.1 记忆读写
- 文件 CRUD：创建、读取、更新、删除记忆文件
- 索引管理：MEMORY.md 在添加/删除记忆后正确更新
- 截断：超过 200 行或 25KB 时正确截断并追加 WARNING
- 路径安全：`name` 含 `../` 或特殊字符时拒绝写入

### 10.2 记忆注入
- system message 中包含 MEMORY.md 内容
- `load_memory` 返回正确的文件内容
- 不存在的 memory_name 返回 not-found 消息

### 10.3 提取器
- 对话中有用户偏好时，自动创建 user 类型记忆
- 对话中有纠正时，自动创建 feedback 类型记忆
- 不提取代码模式或临时信息
- 与主 Agent 写入的互斥正确

### 10.4 梦境整理
- 时间门控：不足 24h 不触发
- 会话门控：不足 5 次不触发
- 锁门控：已有锁时不触发
- stale 锁超过 1h 可被抢占
- 整理失败时正确回滚
- 整理后 MEMORY.md 不超过限制
