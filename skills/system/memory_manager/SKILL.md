# Memory Manager — 持久化记忆系统

## 为什么需要这个 Skill

Claude 没有跨会话记忆。每次对话都从空白开始。这意味着：

- 上次费力调试出来的环境配置，今天又要重新摸索
- 用户已经说过"我不喜欢用 TypeScript"，但下次又忘了
- 项目里那个奇葩的 API 限制，每次都要重新踩坑

**Memory Manager 通过把重要信息写到文件系统来解决这个问题。**
`./memory` 目录就是 Claude 的外部大脑。

---

## 三个核心动作

### 1. 任务开始 → 读取记忆

在开始执行任何实质性任务前，先检查是否有相关记忆：

```bash
# 查看记忆目录全貌
ls -la ./memory/ 2>/dev/null || echo "记忆目录尚不存在"

# 读取与当前任务相关的记忆文件
cat ./memory/<相关文件>.md 2>/dev/null
```

读到相关记忆后，在脑中整合，**不需要把全部内容复述给用户**，直接体现在你的行动里。可以简短说一句："我看了一下之前的记录，继续上次的进度。"

### 2. 任务过程中 → 随时写入

遇到下面这些情况，立即写入记忆，不要等到任务结束：

| 触发场景 | 写入什么 |
|---------|---------|
| 用户纠正了你的做法 | 用户的真实偏好和原因 |
| 踩了一个坑并解决了 | 问题描述、根因、解决方案 |
| 发现了重要的项目结构/配置 | 目录布局、关键文件路径、约定 |
| 做出了有影响的架构决策 | 决策内容、考虑的选项、选择理由 |
| 用户提供了关键背景 | 业务约束、技术限制、团队习惯 |
| 发现了外部依赖的奇特行为 | API 限制、版本兼容问题、已知 bug |

### 3. 任务结束 → 整理归档

任务完成后，花 30 秒把本次新增的信息整理一下，确保格式清晰、日期标注正确。

## 文件组织结构

```
./memory/
├── project.md          # 项目概览：目标、架构、关键决策
├── preferences.md      # 用户偏好：语言、风格、工具选择
├── pitfalls.md         # 踩坑记录：遇到的问题和解决方案
├── context.md          # 背景信息：业务逻辑、团队约定、外部约束
└── <topic>.md          # 其他主题文件（按需创建）
```

**命名原则：**
- 用英文小写文件名，方便跨平台
- 一个文件聚焦一个主题
- 宁可多建文件，不要把无关内容混在一起

---

## 记忆文件格式规范

每个记忆文件遵循统一格式，方便快速扫描：

```markdown
# <主题名称>

_最后更新：YYYY-MM-DD_

## <子主题>

**[YYYY-MM-DD]** 简短摘要

具体内容，包括：
- 关键事实
- 上下文
- 注意事项

---

## <另一个子主题>

...
```

**写作要求：**
- 用**中文**（除非用户明确使用其他语言）
- 每条记忆标注日期
- 写**原因**，不只写结论（"用 pnpm 因为项目用了 monorepo"比"用 pnpm"有用得多）
- 足够简洁：未来的 Claude 需要快速扫描，不是阅读小说

---

## 何时写、何时不写

**✅ 应该写入记忆：**
- 用户明确说"记住这个" / "下次也这样"
- 你犯了错，用户纠正了你
- 发现了不直观的系统行为（需要摸索才能知道的）
- 做出了会影响后续工作的重要决定
- 用户透露了项目背景、业务约束、个人偏好
- 解决了一个可能反复出现的问题

**❌ 不必写入记忆：**
- 可以轻易从代码/文档推断出来的信息
- 一次性任务的临时中间结果
- 非常通用的知识（不是这个项目/用户特有的）
- 用户说"只是这次"的临时调整

## 实际操作示例

### 示例 A：读取记忆后执行任务

```
用户：帮我给这个项目加一个用户认证功能

Agent 动作：
1. cat ./memory/project.md   # 了解项目架构
2. cat ./memory/preferences.md  # 了解技术偏好
3. 发现项目用 FastAPI + PostgreSQL，用户偏好不用 ORM
4. 直接用 asyncpg 写 SQL，不引入 SQLAlchemy
```

### 示例 B：踩坑时写入记忆

```bash
# 发现 Docker build 在 M1 Mac 上有架构问题，解决后立即记录
cat >> ./memory/pitfalls.md << 'EOF'

## Docker 构建问题

**[2024-01-15]** M1 Mac 上 Docker build 报 `exec format error`

需要在 docker build 时加 --platform linux/amd64 标志：
```bash
docker build --platform linux/amd64 -t myapp .
```
根因：基础镜像没有 arm64 版本，需要强制指定平台。

---
EOF
```

### 示例 C：记录用户偏好

```bash
mkdir -p ./memory
cat > ./memory/preferences.md << 'EOF'
# 用户偏好

_最后更新：2024-01-15_

## 代码风格

**[2024-01-15]** 不喜欢过度抽象

用户明确说："不要为了设计模式而设计模式，能用函数解决的不要非得搞类"。
保持代码平铺直叙，只在真正有复用需要时才抽象。

## 工具选择

**[2024-01-15]** 包管理器用 pnpm

项目是 monorepo 结构，pnpm workspace 是团队标准。不要建议换成 npm/yarn。

---
EOF
```

## 记忆维护

### 更新已有记忆

不要删除旧记录，在原文件追加新内容，保留历史：

```bash
# 追加到现有文件
cat >> ./memory/project.md << 'EOF'

## 认证模块（新增）

**[2024-01-20]** 采用 JWT + Redis 存储黑名单的方案

考虑过 session-based，但因为要支持多实例部署，选了 JWT。
Token 过期时间 24h，刷新 Token 7 天。

EOF
```

### 定期清理

记忆文件不会自动清理。当文件变得很长时，可以：
1. 把明显过时的记录标记为 `~~删除线~~`
2. 创建 `archive/` 子目录存放旧内容
3. 保留摘要，删除过于细节的历史

## 快速参考

```bash
# 查看所有记忆文件
ls ./memory/

# 搜索特定关键词
grep -r "docker" ./memory/

# 查看某文件最后修改时间
stat ./memory/project.md

# 一次性显示所有记忆（任务开始时的全量加载）
find ./memory -name "*.md" -exec echo "=== {} ===" \; -exec cat {} \;
```

## 和用户的沟通方式

- **读取记忆时**：不必每次都告诉用户"我在读记忆"，除非读到了影响决策的关键信息，才简短提一下："根据之前的记录，你们用的是 pnpm……"
- **写入记忆时**：可以告知用户，比如"我把这个坑记下来了，下次不会再踩"，让用户感受到记忆系统在工作
- **记忆有冲突时**：主动和用户确认，不要默默覆盖旧记忆

---

记忆系统的价值在于**积累**。每次任务都比上次更了解这个项目和这个用户。
