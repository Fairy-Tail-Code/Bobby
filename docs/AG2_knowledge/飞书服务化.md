# 飞书服务化架构

## 概述

将 AG2 OpenHarness 从 CLI 工具改造为飞书机器人常驻服务。用户通过飞书（群聊或单聊）与机器人交互，后台每个聊天对应独立的 4-agent swarm 会话，单进程多协程并发。

## 启动方式

```bash
python server.py
```

前置条件：
- `.env` 配置 `FEISHU_APP_ID` 和 `FEISHU_APP_SECRET`
- `config/harness.yaml` 的 `hitl.mode` 设为 `feishu`
- MCP 服务器在 `config/mcp.yaml` 中配置

## 组件详解

### 1. FeishuBotService (`infrastructure/feishu_bot.py`)

**职责**：飞书消息收发的唯一出口。

**初始化流程**：
1. 创建 `lark.Client`（用于 REST API 发送消息）
2. 注册 `im.message.receive_v1` 事件处理器
3. 创建 `lark.ws.Client`（WebSocket 长连接接收消息）
4. 在 daemon 线程中启动 WS Client（独立事件循环）

**消息接收流程**：
```
飞书 WS → _on_ws_message() [WS 线程]
  → 忽略 bot 自己的消息 (sender_type == "app")
  → 群聊只响应 @机器人 的消息，并去除 @_user_X 前缀
  → 非文本消息回复"暂不支持"
  → run_coroutine_threadsafe(on_message, main_loop)
  → SessionManager.handle_message() [主事件循环]
```

**为什么 WS 在独立线程**：
lark-oapi 的 WS Client 内部调用 `loop.run_until_complete()`，如果在已运行的事件循环上调用会抛 `RuntimeError: This event loop is already running`。所以必须创建新事件循环并覆盖模块级 `ws_mod.loop` 变量。

**线程安全桥接**：
- `set_main_loop(loop)` 在启动时保存主事件循环引用
- WS 线程中用 `asyncio.run_coroutine_threadsafe(callback, main_loop)` 将异步回调调度到主循环
- 所有 `inject_reply`、`handle_message` 都在主循环上串行执行，无需锁

### 2. ChannelFeishuService (`infrastructure/channel_feishu_service.py`)

**职责**：实现 `ChannelAdapter` ABC，用 asyncio.Future 替代 polling。

**核心机制**：
```python
# 发送消息时创建 Future
async def send(self, recipient, subject, body, request_id):
    self._pending_futures[request_id] = loop.create_future()
    await self._bot.send_text(self._chat_id, text)

# 等待回复（替代 polling）
async def wait_reply(self, request_id, timeout=3600):
    return await asyncio.wait_for(future, timeout=timeout)

# 注入飞书用户回复
def inject_reply(self, request_id, text):
    future.set_result(text)
```

**为什么 Future 而非 polling**：
旧的 `channel_feishu.py` 每 30 秒轮询一次 `_replies` 字典。这在服务模式下浪费资源且延迟高。Future 是零开销的——没有回复时完全不消耗 CPU。

**安全前提**：`wait_reply`（agent 侧）和 `inject_reply`（飞书消息侧）都在同一个 asyncio 事件循环上运行。CPython 的 asyncio 保证 `set_result` 和 `await` 串行化，无需额外同步。如果未来 `inject_reply` 从其他线程调用，需要改用 `loop.call_soon_threadsafe`。

### 3. SwarmSession (`infrastructure/swarm_session.py`)

**职责**：单个飞书聊天的完整 swarm 生命周期。

**生命周期**：
```
start(prompt)
  → asyncio.create_task(_run())
    → _create_agents()     # 创建 4 AI agents + 4 channel proxies
    → _start_message_monitor()  # 启动消息监控协程
    → a_initiate_group_chat()   # 运行 swarm
    → _save_session()           # 保存聊天记录
    → monitor_task.cancel()     # 停止监控
  → 终止时：task.cancel() → CancelledError
```

**Agent 创建**：
- 每个会话独立创建一套 agents（不复用），通过 `create_pm_agent` 等工厂函数
- 4 个 ChannelUserProxyAgent 共享同一个 `ChannelFeishuService` 实例
- `recipient` 参数设为 `chat_id`（而非 open_id），因为消息都发到同一个聊天
- MCP tools 共享全局 `McpManager`

**消息监控**（`_monitor_messages`）：
- 每 1 秒轮询所有 AI agent 的 `chat_messages` 属性
- 检测新增消息并推送到飞书
- 跳过 tool 角色消息（只显示工具名称，不显示完整结果）
- 跳过 Transfer/TERMINATE 等控制消息

**为什么不用 register_reply**：
AG2 的 `register_reply` hook 在 agent **生成回复之前**触发。`messages[-1]` 是触发消息（上一个 agent 的输出），不是当前 agent 的输出。这意味着：
1. 每个 agent 的 hook 推送的是收到的消息，不是自己的输出
2. 同一条消息被多个 agent 重复推送
3. Agent 的实际输出永远不会被捕获

这是 AG2 的架构限制：没有 post-reply hook。`process_all_messages_before_reply` 也是 pre-processing。因此只能用轮询 agent.chat_messages 的方式间接获取 agent 输出。

### 4. SessionManager (`infrastructure/session_manager.py`)

**职责**：管理多个 SwarmSession，路由飞书消息。

**消息路由逻辑**（隐式模式）：
```
handle_message(chat_id, open_id, chat_type, text)
  if text ∈ {"终止", "停止", "abort", "cancel", "stop"}:
    → session.terminate()
  elif 有活跃 session:
    → session.inject_reply(text)  # 注入到等待中的 channel proxy
  else:
    → _create_session(chat_id, text)  # 以 text 为 prompt 创建新 session
```

**Session 清理**：
- 创建新 session 时，先清理同一 chat_id 的旧 session（调用 `old._channel.stop()`）
- `terminate_all()` 用于服务关闭时批量清理

### 5. server.py

**职责**：服务入口，组装所有组件。

**启动顺序**：
1. 加载配置（`.env` + YAML）
2. 设置主事件循环引用（给 FeishuBotService 的 WS 线程桥接用）
3. 初始化 SkillRegistry
4. 连接 MCP 服务器（全局共享）
5. 创建 SessionManager
6. 创建 FeishuBotService，设置 on_message 回调为 session_manager.handle_message
7. 设置 main_loop，启动 bot
8. 等待停止信号（SIGINT/SIGTERM/KeyboardInterrupt）
9. 清理：terminate_all + mcp_manager.disconnect_all

## 飞书端使用方式

### 单聊
- 用户在飞书搜索机器人，直接发消息
- 所有消息都会触发机器人响应

### 群聊
- 把机器人拉进飞书群
- 必须 `@机器人` 发消息才会响应
- 飞书会将 @mention 替换为 `@_user_X` 格式，代码中用正则 `r"@_user_\d+\s*"` 去除

### 命令

| 消息 | 效果 |
|------|------|
| 任意文字（无活跃 session） | 创建新任务，文字作为 prompt |
| 任意文字（有活跃 session） | 注入到等待中的 channel proxy |
| `终止` / `停止` / `abort` / `cancel` / `stop` | 终止当前任务 |

### 消息展示

- Agent 的 LLM 文本输出：`【PM】\n你好，我来帮你梳理需求...`
- 工具调用：`🔧 **PM** 正在执行工具: \`workspace_list\``
- 工具结果：**不展示**（只展示调了什么工具）
- Agent 间 handoff 消息：不展示（Transfer to XXX 是控制消息）

## 与现有代码的关系

### 保留不动的文件
- `infrastructure/channel_feishu.py` — 旧的 polling 飞书通道，仍用于 CLI 模式
- `main.py` — CLI 入口，不受影响
- `orchestration/group.py` — CLI 模式的 swarm 编排
- `agents/factory.py` — `create_all_agents` 仍被 CLI 使用

### 改动的文件
- `agents/channel_proxy.py` — `a_get_human_input` 新增 isinstance 分支，兼容新旧两种 channel

### 复用的函数
- `create_pm_agent`、`create_planner_agent` 等（from `agents/factory.py`）
- `setup_handoffs`（from `agents/factory.py`）
- `_register_context_transforms`（from `agents/factory.py`）
- `ChannelUserProxyAgent`、`ROLE_DESCRIPTIONS`（from `agents/channel_proxy.py`）

## 已知限制

1. **消息监控有 ~1 秒延迟**：轮询 agent.chat_messages，不是实时推送
2. **不支持暂停**：asyncio.Task 暂停复杂，只支持终止
3. **不支持流式输出**：飞书消息 API 不支持流式编辑
4. **无用户认证**：任何飞书用户都可以直接使用
5. **无 Session 持久化**：服务重启后所有会话丢失
6. **MCP 并发**：所有 session 共享同一个 McpManager，MCP 工具调用是串行的
