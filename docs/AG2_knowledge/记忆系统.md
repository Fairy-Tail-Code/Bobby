# AG2 记忆系统

## 1. 目标

在 AG2 项目里，长期记忆不要只靠 prompt 口头要求模型“自己去读写文件”，更稳妥的做法是把记忆实现成明确的基础设施：

- 有固定目录
- 有统一索引入口
- 有显式工具
- 有 system prompt 注入

这正是 `cc-haha` 的核心做法。

## 2. cc-haha 的关键结构

`cc-haha` 的记忆系统可以拆成 5 个基础块：

1. `paths`：解析 auto-memory 根目录
2. `memdir` / prompt builder：把 memory 指令和 `MEMORY.md` 注入 system prompt
3. `memoryScan`：扫描记忆文件、解析 frontmatter、生成 manifest
4. `findRelevantMemories`：按查询挑选相关记忆
5. `extractMemories` / `autoDream`：后台自动提取和整理

它的核心思想不是向量库，而是：

- 文件系统持久化
- `MEMORY.md` 做入口索引
- Markdown + frontmatter 做可读可编辑存储

## 3. 在 AG2 中如何落地

对于 AG2 项目，最小可用实现通常分三层：

### 3.1 记忆文件层

需要提供：

- `save_memory(name, content, memory_type, description)`
- `load_memory(memory_name)`
- `MEMORY.md` 自动维护

### 3.2 Prompt 注入层

在创建 `ConversableAgent` 后，将记忆块追加到 `system_message`：

```python
agent.update_system_message(agent.system_message + "\n\n" + memory_block)
```

注入内容至少应包含：

- memory 目录位置
- 哪些内容值得记忆
- 四类记忆说明
- 当前 `MEMORY.md` 索引

### 3.3 Tool 注册层

AG2 中最好把记忆能力注册为 Tool，而不是只写在 prompt 中：

```python
Tool(...).register_for_llm(agent)
Tool(...).register_for_execution(agent)
```

这样模型拿到的是明确可调用的能力，不再依赖它先想起某个 skill。

## 4. Bobby 本次适配方式

`Bobby` 本次选择的是“先落读写层，再扩自动化”：

- 新增 `infrastructure/memory/`
- 每个核心 Agent 自动注入 `Project Memory`
- 每个核心 Agent 自动注册 `load_memory` / `save_memory`
- `MEMORY.md` 保存时自动重建
- 兼容旧 `user_profile.md`

同时同步打通三条 AG2 创建路径：

- `agents/factory.py`
- `infrastructure/agent_pool.py`
- `infrastructure/session/agent_session.py`

其中第三条在当前架构里已经不再是“直接在 session 类里创建并运行 swarm”，
而是由 `AgentSession` 作为会话壳层，统一衔接 single / network 两种 runtime 的记忆收尾路径。

## 5. 为什么不要只靠 skill

skill 适合“额外工作流指南”，不适合承担“基础设施入口”。

如果记忆只在 skill 里：

- 模型可能压根不去加载 skill
- 多 Agent 下行为不一致
- prompt 一旦变动，记忆能力容易失效

如果记忆是 Tool + prompt injection：

- 每个 Agent 都有相同入口
- 结构可测试
- 运行路径更稳定

## 6. 后续扩展建议

如果要继续对齐 `cc-haha`，推荐顺序：

1. 会话结束自动提取新记忆
2. `memory` 写锁和消息游标跳过
3. dream consolidation 定时任务
4. 项目 / 用户 / 团队三级目录拆分

## 7. Bobby 当前的自动抽取实现

`Bobby` 现在已经补上了一个最小可用的自动抽取链路，但它不是在主对话里增加一个新 agent，而是作为 session 后处理步骤执行：

- session `completed` 或 `terminated` 后收集消息
- 调用独立 extractor prompt 提炼 durable memories
- 输出结构化 JSON：`name / memory_type / description / content`
- 复用 `save_memory_file(...)` 写入现有 memory 目录
- 自动重建 `MEMORY.md`

这样做的优点是：

- 不破坏现有 swarm / single 主流程
- 不引入第二套记忆格式
- 自动抽取与手动 `save_memory` 共用同一套落盘逻辑

另外，`Bobby` 现在对同名 memory 采用“先合并再写”的策略：

- 自动抽取先产出候选 memory
- 如果同名 memory 已存在，则读取旧文档
- 用 merge prompt 生成最终版本
- 若结果与旧内容等价，则跳过写回

这比简单覆盖更接近 `cc-haha` 的演进式记忆维护方式。
